  핵심 매핑 (Core NATS → JetStream)

  ┌────────────────────────────┬────────────────────────────────────────────┐
  │            기존            │                 JetStream                  │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ Subject (휘발)             │ Stream (File storage로 영속)               │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ Service = Queue group 이름 │ Service = Durable Consumer 1개             │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ Instance = 같은 queue      │ Instance = 같은 durable name을 bind한 여러 │
  │ group 멤버                 │  클라이언트                                │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ Fanout = 다른 queue group  │ Fanout = 다른 durable consumer (각자 ack   │
  │                            │ state)                                     │
  └────────────────────────────┴────────────────────────────────────────────┘

  ▎ 핵심: JetStream에서는 "queue group" 문자열이 따로 없습니다. 같은 durable 
  ▎ consumer를 여러 클라이언트가 share하는 게 queue group 역할을 합니다.

  결정해야 할 분기점

  1. Consumer 방식: Pull (모던/권장) vs Push (legacy의 DeliverGroup) → Pull 추천
  2. Storage: File (영속) vs Memory → File 필수 (유실 방지가 목적이니)
  3. AckPolicy: AckExplicit + 적절한 AckWait/MaxDeliver

  PoC가 검증해야 할 시나리오 3가지

  1. Baseline: fanout O + service 내 1 instance만 처리 O (기존과 동일)
  2. Downtime test ← PoC 핵심: serviceB 전체 종료 → publish → serviceB 재시작 →
  누락 없이 전부 수신
  3. Mid-processing crash: ack 전 인스턴스 죽음 → 다른 인스턴스가 재수신
  (AckWait 동작)
