# 배운 점

## 1. API 가능성과 운영 안전성은 다른 질문이다
시스템이 update API 를 제공한다고 해서, 그 경로가 라이브 마이그레이션에 안전하다는 뜻은 아니다.
이번 스터디가 더 유의미해진 지점은 질문이 "이 config 를 바꿀 수 있는가"에서 "이걸 운영 중 안전하게 전환할 수 있는가"로 바뀐 순간이었다.

## 2. 실패한 경로도 중요한 결과다
이번 스터디에서 최종 전략을 만든 핵심은 세 가지 실패 결과였다.

- in-place retention mutation 은 서버가 거부했다
- consumer update 는 본질적 제약을 해결하지 못했다
- delete/recreate 는 유지되어야 할 상태를 잃게 만들었다

즉 실패한 실험이 헛수고가 아니라, 위험한 선택지를 의사결정 트리에서 제거해 준 셈이다.

## 3. Consumer 생성 시점은 설계 변수다
Interest 기반 경로에서는 consumer 를 언제 붙이느냐가 마이그레이션 안전성에 직접 영향을 줬다.
이건 설정 문법만 보면 놓치기 쉽고, happy path 가정만 하면 더 잘 놓치는 종류의 제약이다.

## 4. Rollback 은 의도적으로 보존해야 한다
rollback 은 old 경로가 실제로 남아 있어야만 의미가 있다.
old 경로를 너무 빨리 지워버리면, 문서상으로는 rollback 이 있어 보여도 실제 운영에서는 안전망이 사라진다.

## 5. 마이그레이션은 종종 교체보다 공존의 문제다
이번 경우 더 안전한 경로는 한 번에 바꾸는 스위치가 아니었다.
핵심은 일정 기간의 통제된 공존이었다.

- 새 경로를 먼저 도입하고
- old 경로를 유지한 채
- overlap 상태에서 동작을 관찰하고
- 충분히 확인된 뒤 컷오버하는 방식

## 6. 이번 스터디가 강화한 기술 습관
플랫폼 동작이 중요할수록, 추측을 작은 재현 가능한 실험으로 바꾸는 습관이 중요하다.
이 습관 덕분에 막연한 아키텍처 고민이, 제약이 분명하고 순서가 정리된 실제 마이그레이션 전략으로 바뀌었다.

## 최종 요약

이번 스터디는 불확실성을 줄여가는 과정의 기록이다.

1. 가장 직접적인 경로를 먼저 테스트하고
2. 왜 실패하는지 확인하고
3. 진짜 제약이 무엇인지 찾아내고
4. 더 안전한 대안을 다시 검증하고
5. 최종적으로 운영 절차로 정리한다

최종 답도 중요하지만, 이 과정을 반복 가능한 방식으로 남긴 것이 더 중요하다.
