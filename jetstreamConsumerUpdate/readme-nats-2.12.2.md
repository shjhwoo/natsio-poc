# 운영 중 Consumer의 FilterSubjects 런타임 변경 PoC 검증 계획서

## 검증 목적

> "이미 운영 중인(메시지를 소비하고 있는) Consumer의 구독 주제(FilterSubjects)를,
> 서비스 재시작 없이 런타임에 바꿀 수 있는가?"

대표님이 실제로 물어본 핵심 케이스는 **subject `a`를 `b`로 완전히 교체**(겹치는 subject 없음)하는 경우다.
넓히기/좁히기보다 이 "완전 교체"가 가장 자명하지 않으므로 반드시 포함한다.

Durable / Ephemeral 두 종류 모두 실험해 거동을 비교한다.
(상태 저장 위치가 서버 vs 프로세스로 다르므로 결과가 다를 수 있다는 가설)

---

## 환경

| 항목               | 값                                                     |
| ------------------ | ------------------------------------------------------ |
| NATS Server        | 2.12.2                                                 |
| nats.go 클라이언트 | v1.52.0                                                |
| Retention Policy   | LimitsPolicy (InterestPolicy는 이번 PoC에서 미검증)    |
| Storage            | MemoryStorage (FileStorage는 이번 PoC에서 미검증)      |
| DeliverPolicy      | **DeliverAllPolicy** — 전 케이스 공통. 아래 주석 참고. |

> ⚠️ FilterSubjects 업데이트 지원은 NATS 2.10+부터 가능. 2.10 미만에서는 거부됨.

> **DeliverAllPolicy 선택 이유**: "운영 중에 이미 메시지를 소비하고 있는 컨슈머"를 시뮬레이션하기 위해 사용.
> 스트림에 메시지를 미리 쌓은 뒤 컨슈머를 붙이면 과거 메시지를 모두 수신 가능한 상태가 된다.
> DeliverNewPolicy였다면 AckFloor=0 상태에서 filter를 변경하게 되어 완전 교체의 위험성(AckFloor 오염)이 드러나지 않는다.

---

## 사전 확인 사항 (결과)

- **FilterSubject vs FilterSubjects**: `FilterSubjects`(복수형) 사용. 다중 subject 지정 및 업데이트 모두 지원.
- **업데이트 API**: `CreateOrUpdateConsumer`에 동일 Durable/Name + 변경된 FilterSubjects를 전달하면 업데이트로 처리됨. 거부 없음. `nats consumer edit` CLI도 동일 서버 API를 호출하므로 결과 동일.
- **Ephemeral의 이름**: Durable을 설정하지 않아도 `Name` 필드로 이름을 지정할 수 있음(NATS 2.10+). 이름이 있으면 in-place 업데이트 가능. 이름 없는 Ephemeral도 서버가 이름을 할당하며, 그 이름을 알면 업데이트 가능 — 단 실무에서는 이름을 미리 알 수 없어 사실상 의미 없음.

## 공통 셋업

```
Stream: FILTER_TEST
Subjects: test.a, test.b, test.c
Retention: LimitsPolicy  Storage: MemoryStorage
각 Phase 시작 전 스트림 Purge로 초기화
발행 패턴: 인터리브 (a1,b1,c1,a2,b2,c2,...,a5,b5,c5) — 5라운드, 총 15개
  → Purge 후에도 stream seq는 리셋되지 않으므로 실제 seq는 phase마다 다름
  → 인터리브 이유: AckFloor(stream global seq 기반)와 새 subject 간 충돌을 가시화하기 위함
```

### 대표 유즈케이스 3가지 (방향성 기준)

어떤 복잡한 변경이든 결국 아래 세 방향의 조합이다. 이 3개만 검증하면 나머지는 추론 가능.

| #   | 케이스          | 예시                    | 방향                                            |
| --- | --------------- | ----------------------- | ----------------------------------------------- |
| 1   | **추가**        | `[b, c]` → `[a, b, c]` | 관심 범위 넓힘 (기존 유지 + a 추가)             |
| 2   | **제거**        | `[a, b, c]` → `[a, b]` | 관심 범위 좁힘 (c만 뺌)                         |
| 3   | **완전 교체** ★ | `[a]` → `[b]`           | 겹침 0, 들어내고 갈아끼움 (제거+추가 동시·극단) |

핵심은 3번이다. "제거 + 추가가 겹침 없이 동시에" 일어나는 가장 극단이라 ack 커서 거동이 가장 안 자명하다.

## Part 1 — Durable Consumer

### Phase D-1 — 추가 ([b, c] → [a, b, c])

|                  |                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **시나리오**     | Durable(filter=[b, c], DeliverAll) 생성 → b,c 합쳐 5개 ack(b:3, c:2) → filter를 [a, b, c]로 업데이트                                                               |
| **확인 포인트**  | ① 에러 없이 적용되는가 ② 기존 b, c의 ack 위치는 유지되는가 ③ 새로 추가된 a는 과거 메시지를 전부 받는가, AckFloor 이후 것만 받는가                                   |
| **실제값**       | ① 성공 ② b 나머지=2(기대2) c 나머지=3(기대3) — 유지됨 ③ a 수신=**2개만**(a-004, a-005). a-001~003은 AckFloor.Stream=8 이하라 skip됨. NumPending: 5 → 7(a 2개 추가) |
| **결론**         | 업데이트 성공. 기존 ack 위치 완전 보존. **단, 새로 추가된 subject도 기존 AckFloor의 영향을 받아 AckFloor 이전 과거 메시지는 수신 불가.** 이 점은 추가 케이스의 함정. |

### Phase D-2 — 제거 ([a, b, c] → [a, b])

|                  |                                                                                                                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **시나리오**     | Durable(filter=[a, b, c], DeliverAll) 생성 → a,b,c 각 2개씩 총 6개 ack → test.c pending 3개 남긴 상태 → filter를 [a, b]로 업데이트(c 제거)                                               |
| **확인 포인트**  | ① 적용되는가 ② 제거된 c의 NumPending이 어떻게 되는가 ③ 남은 a, b의 ack 위치 영향 없는가                                                                                                  |
| **실제값**       | ① 성공 ② NumPending: 9 → 6 (차이=3 — c pending 3개 **즉시 제거**. 스트림에는 잔류하나 이 컨슈머 관심에서 제외) ③ a 나머지=3(기대3), b 나머지=3(기대3) — 무영향. c 메시지 0개 수신 확인 |
| **결론**         | 업데이트 성공. filter에서 제거된 subject의 pending은 즉시 해소. a,b ack 위치 완전 무영향. 제거는 가장 안전한 케이스.                                                                      |

### Phase D-3 — 완전 교체 ([a] → [b]) ★ 핵심

|                  |                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **시나리오**     | Durable(filter=[a], DeliverAll) 생성 → test.a 3개 ack(a-001~003) → filter를 [b]로 완전 교체                                                                                                                                                                                                                                                                           |
| **확인 포인트**  | ① 교체가 에러 없이 되는가 ② AckFloor.Stream이 리셋되는가 ③ test.b 메시지를 몇 개 받는가(b 5개 전부 vs AckFloor 이후 것만)                                                                                                                                                                                                                                             |
| **실제값**       | ① **성공** (거부 없음) ② AckFloor.Stream: 37 → **37 그대로** (리셋 없음) ③ b 수신=**3개만**(b-003~005, seq 38,41,44). b-001(seq32), b-002(seq35)는 AckFloor(37) 이하 → **영구 skip**. NumPending: 2 → 3                                                                                                                                                              |
| **결론**         | **업데이트는 성공하지만 데이터 손실 발생.** AckFloor는 stream 전체의 global seq 기반으로 관리되며, subject 교체 시 리셋되지 않는다. a 소비로 쌓인 AckFloor가 b에도 그대로 적용되어, AckFloor 이하의 b 메시지(b-001, b-002)는 이 컨슈머에 영구적으로 전달되지 않는다. **DeliverAllPolicy라도 완전 교체는 손실 없이 할 수 없다. 완전 교체가 필요하면 컨슈머 재생성이 안전.** |

### Phase D-4 — 업데이트 전후 상태 비교 (공통 측정)

|            |                                                                                                                                                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **측정값** | NumPending, AckFloor.Stream (업데이트 전/후)                                                                                                                                                                                      |
| **실제값** | D-1: AckFloor 유지(8→8), NumPending 증가(5→7) / D-2: AckFloor 유지(21→21), NumPending 감소(9→6) / D-3: AckFloor 유지(37→37), NumPending 재계산(2→3)                                                                              |
| **결론**   | **AckFloor.Stream은 filter 변경 시 절대 리셋되지 않는다.** NumPending은 새 FilterSubjects를 기준으로 즉시 재계산된다. "구독 주제는 바뀌지만 읽은 위치(커서)는 그대로"가 핵심 동작 원리이며, 이것이 완전 교체 시 손실의 근본 원인. |

## Part 2 — Ephemeral Consumer

> **전제 수정**: 계획서 작성 당시 "Ephemeral은 식별 이름이 없다"고 가정했으나, NATS 2.10+에서는
> `Name` 필드만 설정하고 `Durable` 미설정으로 **Named Ephemeral** 생성이 가능하다.
> Unnamed / Named 두 케이스로 나눠 검증했다.

### Phase E-0 — Unnamed Ephemeral (Name/Durable 모두 미설정)

|                  |                                                                                                                                                                                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **시나리오**     | Name/Durable 미설정으로 Ephemeral 생성 → 서버가 랜덤 이름 할당 → 그 이름으로 FilterSubjects 업데이트 시도                                                                                                                                                            |
| **확인 포인트**  | 서버 할당 이름으로 in-place 업데이트 가능한가                                                                                                                                                                                                                        |
| **실제값**       | 서버 할당 이름 `Ty7ToKdN` 확인. Durable=""(미설정), InactiveThreshold=1m. 그 이름을 `Name` 필드에 넣어 업데이트 시도 → **성공**. NumPending: 3 → 7. AckFloor 유지.                                                                                                   |
| **결론**         | 기술적으로는 서버 할당 이름을 알면 in-place 업데이트 가능. **단 실무에서 의미 없음**: 서버 할당 이름은 생성 응답에서만 알 수 있고, 연결이 끊기면 컨슈머가 만료되어 이름도 사라진다. filter 변경이 필요한 시점에 이름을 보장할 수 없으므로 재생성 패턴이 사실상 강제된다. |

### Phase E-1 — Named Ephemeral (Name 지정, Durable 미설정)

|                  |                                                                                                                                                                                                                                         |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **시나리오**     | `Name="eph-named-test"` 설정(Durable 미설정) → 추가/제거/완전교체 3케이스 각각 in-place 업데이트 시도                                                                                                                                   |
| **확인 포인트**  | ① 3케이스 모두 업데이트 성공하는가 ② Durable과 동일한 거동인가 ③ ack 상태 유지되는가                                                                                                                                                    |
| **실제값**       | 추가[a]→[a,b]: 성공, NumPending 3→7, AckFloor 유지 / 제거[a,b,c]→[a,b]: 성공, NumPending 13→8(c pending 5개 제거), AckFloor 유지 / 완전교체[a]→[b]: 성공, NumPending 3→4(AckFloor 이하 b 1개 skip), AckFloor 유지                      |
| **결론**         | **Named Ephemeral은 filter 변경 거동이 Durable과 완전히 동일.** AckFloor 유지, NumPending 재계산, 완전 교체 시 AckFloor 이하 메시지 skip까지 동일. Durable과의 유일한 차이는 InactiveThreshold 이후 자동 만료 여부. ack 상태는 유지됨. |

## AckFloor 오염 메커니즘 (D-3 핵심 원리)

```
발행(인터리브):  a1  b1  c1  a2  b2  c2  a3  b3  c3 ...
stream seq:      31  32  33  34  35  36  37  38  39 ...

filter=[a], DeliverAll → a만 수신: seq 31(a1), 34(a2), 37(a3), 40(a4), 43(a5)
a 3개 ack: seq 31, 34, 37 → AckFloor.Stream = 37

filter=[b]로 교체:
  b seq: 32(b1), 35(b2) < AckFloor(37) → 서버는 이미 처리된 것으로 간주 → 전달 안 함
  b seq: 38(b3), 41(b4), 44(b5) > AckFloor(37) → 전달됨

결과: b 5개 중 2개 영구 손실
```

AckFloor는 subject별로 분리 관리되지 않고 **stream 전체의 global seq** 기준이다.
filter를 바꿔도 이 커서는 리셋되지 않는다.

## 강의(13-A강)에 반영할 결론 (확정)

**런타임 in-place 업데이트는 된다. 단 완전 교체는 데이터 손실 위험이 있다.**

- **추가/제거**: 안전. 기존 ack 위치 보존, NumPending 즉시 재계산.
  - 단 추가 시: 새 subject의 AckFloor 이전 과거 메시지는 받지 못함. 과거 메시지가 필요하면 재생성 필요.
- **완전 교체**: 업데이트 자체는 성공하나 **AckFloor 오염으로 인해 새 subject의 일부 메시지가 영구 skip된다.**
  - 손실 규모: 교체 전 소비한 subject의 최종 ack seq 위치에 따라 다름.
  - 실무 권고: **완전 교체가 필요하면 컨슈머 재생성 + DeliverPolicy 명시**가 안전.
- **Durable vs Named Ephemeral**: filter 변경 거동 완전히 동일. 차이는 만료 여부뿐.
- **Unnamed Ephemeral**: 실질적으로 in-place 업데이트 불가. filter 변경 = 재생성 = ack 상태 소멸.

## 실행 메모

- NATS 2.12.2, nats.go v1.52.0
- `FilterSubjects`(복수형) 사용. `FilterSubject`(단수형)는 deprecated.
- 업데이트 방법: Go `CreateOrUpdateConsumer` = `nats consumer edit` CLI (동일 서버 API)
- 각 Phase: 스트림 Purge 후 인터리브 발행. Purge는 seq를 리셋하지 않음에 주의.
- 검증 스코프: LimitsPolicy + MemoryStorage. InterestPolicy/FileStorage는 미검증.
